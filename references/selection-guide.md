# 应用选型参考

默认只读前两节；先定位标题再按段读取，按条件读取其余部分，不默认全文加载。不要在本文件固化动态型号、价格或排行榜；回到 SKILL.md 的输出表格与自检交付结果。

## 应用评分与核验深度

按下表控制默认推荐与工作深度；优先完成用户明确指定的厂商、档位、字段及数量。先展示比较全集，再从中选推荐子集，不要混淆两者。

| 评分 | 默认推荐 | 核验深度 | 协作安排 |
| --- | --- | --- | --- |
| 1–2 | 给一个性价比具体型号 | 快速筛选 GPT、DeepSeek、Kimi；打开官方资料核验最终推荐的型号、状态与价格，不遍历全部产品线 | 给直接开工建议；跳过协同规划；不因此实际开工 |
| 3 | 给一主两备 | 核验所有正式比较型号的官方型号与价格资料，以及相关工具能力 | 采用单模型执行建议；可选一次全文交叉评审 |
| 4–5 | 给一至两个主力、二至三个备选 | 覆盖候选厂商完整的任务相关产品线，核验决定选择的基准与部署条件，设计任务样例验证方案 | 从中选二至三个模型安排独立完整规划、交叉评审、汇总与阶段验收 |

在任何评分下都核验真实性、价格和硬约束。对缺失档位保留位置；对证据不足的推荐减少数量并说明。把样例验证设计与实际运行分开，不因分数高就开始业务测试。

## 按项目匹配能力与工具

按目标选择重点；把下表工具名当作检索入口，重新核验正式名称、功能、价格与模型兼容性。

| 类型/条件 | 检查能力 | 考察执行工具 |
| --- | --- | --- |
| 编码/工程 | 检查多文件修改、代码执行/测试、Agent 生态与上下文；按需查 Agentic 编码基准 | 考察 Codex、Claude Code、Kimi CLI/Code、Cursor |
| 金融/数据分析 | 检查数值复算、数据插件、引用追溯、错误处理与私有部署；不声称零幻觉 | 考察带代码、表格和数据连接器的分析/研究 Agent |
| 写作/研究/长文档 | 检查搜索、原文读取、引用定位、长文有效利用和交付格式 | 考察各家 Deep Research、Kimi Work、ChatGPT Work；区分专用研究后台与可选通用模型 |
| 设计/多模态 | 检查所需模态、生成/编辑控制、文件格式和相应计价 | 考察原生多模态工具及实际接入的生成工具 |
| 通用办公/长任务 | 检查文件处理、应用操作、状态恢复、导出及权限 | 考察 Kimi Work、Manus 类、ChatGPT Agent 等工具 |
| 轻量任务 | 检查能否以低成本完成明确定义的输出 | 沿用普通聊天或 API，不新增专门 Agent |
| 中文为主 | 优先考察 Kimi、DeepSeek，按需补充 Qwen，同时保留 GPT；依据任务证据判断 | 核验中文来源可达性与输出能力，不预设品牌排名 |
| 隐私敏感 | 先核验数据出域边界、许可证和部署可行性，继续读取下一节 | 考察符合约束的本地模型与本地工具链 |

## 核验隐私与本地部署

仅在出现隐私、离线、私有化或许可证约束时读取；不受评分高低限制。

- 先明确哪些内容不能离开指定环境；仅用脱敏任务描述做公开检索，不上传受限资料。
- 从官方模型卡/仓库核验精确权重版本或 revision、许可证、商业使用条件、硬件和量化影响，分别检查权重与运行工具。不要把开放权重等同于宽松开源许可或单机可运行。
- 检查外部搜索、遥测、日志、连接器和模型端点的数据流；只在满足约束时推荐。硬件未知时给有条件的配置，不把未验证的本地方案称为可直接部署。
- 对 ≥4 分仍提供二至三个合规模型的协作安排，要求在允许的环境内使用独立会话，不把机密方案送去云端评审。无法核实足够型号时保留空位，禁止放宽隐私条件补数。

## 估算项目成本

仅在用户要求总成本/预算测算，或预算可行性必须靠用量估算判断时读取；日常单价展示直接执行 SKILL.md。

- 先取得或明确假设输入/输出量、调用次数、重试、工具用量与缓存命中率，不把未知用量当事实。
- 使用“输入 token / 1,000,000 × 输入单价 + 输出 token / 1,000,000 × 输出单价 + 其他费用”，按适用档位分别计算缓存、长上下文、批处理、搜索和多模态费用。
- 分开计算 API、订阅与本地算力，避免重复计费，标币种、地区、含税情况与日期；另计协作规划、评审和汇总成本。
- 给出情景区间和主要影响因素，不仅按单 token 价格宣布总成本最低。

## 核对基准与能力证据

仅在用户要求基准对比，或 ≥4 分需用基准支持关键差异时读取；不因评分低而忽略明确的基准请求。

- 打开原始报告，记录具体模型、日期、测试集版本、工具框架、推理预算和重试设置，区分厂商自测、独立测试与推断。
- 比较相同或可解释的设置；无法统一时并列限制，不做伪精确总排名。不把上下文上限或通用榜单成绩等同于项目可靠性。
- 为决定选择的差异设计小型验证与验收标准，仅在已授权时运行；验证前称“待验证的适配判断”，不声称已证明最准确。

## 安排多模型协作

仅在 ≥4 分或用户明确要求协同时读取本节及模板；对 3 分仅在用户选择交叉评审时使用相应模板。

1. 选择二至三个已确认、能力互补的具体型号，尽可能覆盖不同系列，先满足预算、工具与资料传输约束。
2. 整理同一份简报，为方案编号 A/B/C，记录实际模型、会话、工具与日期。
3. 在独立会话中要求各自产出完整规划，提交前不共享方案；不能同时运行时分会话顺序进行并披露，保持独立性。
4. 收齐后将其他方案全文发给每个模型，检查遗漏、风险、依赖、有理由的分歧与亮点；不以摘要代替全文。遇截断先补齐，必要时分批或用可读文件。
5. 汇总全部方案与评审全文，按证据裁决冲突，保留验证步骤和未决事项，不以多数票作事实依据。
6. 实际调用前检查已有授权与工具能力；缺少授权时只交付提示词和回收材料清单，不声称已完成评审。不得借协作安排启动项目业务执行。

### 使用模板一：并行规划

填写已知项目条件，将未知条件保留为待定；仅在已授权时发送，否则交付可粘贴版本。向各模型提供相同简报，仅替换方案编号和模型标识。

```text
为以下项目独立制定完整、可执行的项目规划。在交付方案前不要查看其他模型的方案；不要仅承担一个局部模块。只做规划，不执行对外动作。

使用项目简报：
- 阅读项目目标与背景：[填写]
- 识别项目类型与最终交付物：[填写]
- 按重要性评分考虑失败代价：[填写 1–5 分及理由]
- 遵守预算、期限、隐私、语言、工具与环境约束：[填写；未知项标注未知]
- 使用现有资料：[粘贴资料或提供可访问文件]
- 对照成功与验收标准：[填写]
- 遵守已知依赖和禁止事项：[填写]

以方案 [A/B/C] 输出，并注明实际使用的具体模型版本、工具和日期；无法确定模型版本时明确说明，不要猜测。

依次完成：
1. 复述目标、范围和成功条件，区分事实、假设和待确认项。
2. 提出完整实施路径，解释关键选择，列出替代路径及适用条件。
3. 拆分阶段、工作步骤、依赖、输入、交付物、验收方法和检查点。
4. 列出资源与成本估算的输入、区间和依据，不虚构工作量或精确预算。
5. 识别技术、数据、执行和进度风险，给出应对、停止与回退条件。
6. 检查遗漏环节、潜在反例及最可能失败的假设，提出验证方法。
7. 给出启动清单、关键待决事项和下一阶段进入条件。

仅核验规划必需的动态技术或工具事实并附来源与查询日期；无法核验时标明不确定性。不要开展项目实质研究、构建或数据分析。提交完整方案，使其他评审者无需猜测中间步骤。
```

### 使用模板二：交叉评审

给每个模型发送原始简报、它自己的完整方案及全部其他方案全文；为二模型评审提供一个其他方案，为三模型评审提供两个。

```text
基于相同项目目标，对其他模型的方案进行独立交叉评审。阅读完整内容后再判断，不根据摘要作结论，不因多数模型同意就认可一项主张。

读取以下输入：
- 阅读原始项目简报与验收标准：[粘贴全文]
- 阅读你自己的方案 [编号及具体模型]：[粘贴全文]
- 阅读其他方案 [逐个标注编号及具体模型]：[逐个粘贴完整方案，或提供可完整读取的文件]

先确认已读到每份方案的末尾；若有截断、不可访问文件或缺失段落，指出缺口，待收齐后继续实质评审。

逐份完成以下评审：
1. 指出遗漏的步骤、风险、依赖与验收条件，引用对应章节或原文位置。
2. 指出不同意的关键决策，解释原因、影响及适用条件，给出替代方案或验证办法。
3. 提炼可吸收的亮点，说明它如何改进你的原方案，以及引入后的额外代价。
4. 检查成本、时限、隐私、工具能力和资源假设是否成立；把动态事实核验与推断分开。
5. 说明你自己的方案需要如何修订，并保留仍然成立的分歧。

按“问题/亮点、方案位置、证据或理由、影响、建议、待验证项”组织输出；按影响轻重排序。以可修正的具体判断为主，不做泛泛打分或礼貌性赞同。
```

### 使用模板三：汇总定稿

把原始简报、全部规划方案和全部交叉评审全文交给汇总模型；保持证据与未验证状态可追溯。

```text
综合以下完整材料，制定最终可执行项目规划。按证据、约束和验收标准裁决分歧，不用多数票代替判断，不为消除分歧而拼接互不兼容的方案。

读取以下输入：
- 阅读原始项目简报、硬约束和成功标准：[粘贴全文]
- 阅读所有独立规划方案及其编号/具体模型：[粘贴全文或提供可完整读取的文件]
- 阅读所有交叉评审意见及其评审者标识：[粘贴全文或提供可完整读取的文件]
- 应用后续已确认事实或约束变化：[填写；没有则写无]

先确认材料完整；遇到缺失或截断时索取缺失部分，不宣称已完成全部交叉核验。

依次输出：
1. 给出推荐的最终实施路径与核心选择，简述理由及适用条件。
2. 合并各方案有依据的优点，解决关键依赖冲突，逐阶段写清步骤、输入、责任角色、交付物、验收方式及进入条件。
3. 给出模型与执行 Agent 的交接配置；保留已核验的具体型号，不凭记忆添加版本或价格。
4. 设置需求确认、最小可验证产物、核心功能/证据验收、最终交付检查点，写清停止、回退或升级处理条件。
5. 列出简短决策记录，说明重大建议的采纳/否决理由及对应方案或评审位置。
6. 保留未决事项、待验证假设和会改变最终路径的条件；对关键争议安排验证步骤、责任角色及完成时点。
7. 给出首阶段可直接执行的启动清单，并标明哪些后续阶段仍依赖前置验收。

仅在材料充分且关键冲突已有处理路径时标为“最终规划”；否则标为“条件性规划/待评审”，具体说明剩余依赖。不要把规划完成表述为项目已经执行或验收通过。
```
